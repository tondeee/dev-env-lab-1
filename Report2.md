# Звіт з виконання Лабораторної роботи №2

## Тема
Побудова CI/CD-конвеєра із використанням GitHub Actions.

## Мета
Налаштувати автоматизацію процесів тестування, лінтингу та збірки проєкту за допомогою GitHub Actions, а також організувати публікацію результатів аналізу.

## Виконані завдання

### Частина A: CI для кожного модуля
1. **Створення workflow:** Створено файл `.github/workflows/ci.yml`.
2. **Тригери:** Налаштовано запуск пайплайну при:
   - `push` у гілку `main`.
   - `pull_request` у гілку `main`.
   - Ручному запуску (`workflow_dispatch`) з можливістю вибору конкретного модуля (`all`, `data_load`, `data_quality_analysis`, `data_research`, `visualization`).
3. **Матрична стратегія:** Використано `strategy.matrix` для паралельного запуску 4 модулів.
4. **Оптимізація (Bonus):** Додано фільтрацію за шляхами (`dorny/paths-filter`), що дозволяє запускати лише ті модулі, файли яких були змінені.

### Частина B: CD та публікація результатів
1. **Артефакти:** Після кожного успішного виконання модуля результати (логи, звіти) завантажуються як GitHub Actions artifacts (`actions/upload-artifact@v4`).
2. **GitHub Pages (Bonus):** Налаштовано автоматичне розгортання статичного звіту на GitHub Pages після успішного CI в гілці `main`. Звіт включає згенерований графік розподілу доходів (`income_distribution.png`).
   - *Примітка:* Для коректної роботи деплою необхідно увімкнути GitHub Pages у налаштуваннях репозиторію (`Settings -> Pages -> Build and deployment -> Source -> GitHub Actions`).

### Частина C: Self-hosted runner
1. **Налаштування:** Підключено локальний агент (self-hosted runner) на базі macOS.
2. **Workflow:** Створено окремий файл `.github/workflows/ci-selfhosted.yml` для запуску модуля візуалізації на локальній машині.

## Порівняння GitHub-hosted та Self-hosted runners

На основі реальних запусків у GitHub Actions для модуля `visualization`:

- GitHub-hosted: job `run-modules (visualization)` тривав близько **20 секунд**.
- Self-hosted: після реєстрації локального macOS ARM64 runner і виправлення workflow job `run-visualization-local` тривав близько **26 секунд**.
- Початкові self-hosted запуски чекали runner **24 години** і скасовувались, бо runner не був зареєстрований.

| Характеристика | GitHub-hosted Runner | Self-hosted Runner |
|:--- |:--- |:--- |
| **Час виконання** | **~20 секунд** для job `run-modules (visualization)`. | **~26 секунд** для job `run-visualization-local` після виправлення workflow. |
| **Встановлення залежностей** | **~10 секунд** через `actions/setup-python` і `pip install`. | **~7 секунд** на створення `venv` і встановлення залежностей у локальному середовищі runner. |
| **Запуск модуля** | **~1 секунда**. | **~1 секунда**. |
| **Завантаження артефактів** | **~1 секунда** у межах інфраструктури GitHub. | Потребує відправки з локальної машини в GitHub і залежить від вашого інтернет-каналу. |
| **Доступ до ресурсів** | Тільки через `Checkout`. | Може мати прямий доступ до локальних даних на диску, але це потрібно явно налаштувати у workflow. |
| **Стабільність запуску** | Стабільний, runner доступний одразу. | Потрібно самостійно тримати runner online; інакше job може чекати до 24 годин і бути скасованим. |

### Аналіз результатів
1. **Швидкість:** Для цього невеликого Python-модуля self-hosted runner виявився лише трохи повільнішим за GitHub-hosted runner (`~26 c` проти `~20 c`). Основна різниця - у підготовці середовища.
2. **Доступ до ресурсів:** Перевага self-hosted у доступі до локальних файлів є потенційною, але в поточній реалізації workflow вона ще не використовується повністю. Артефакти обох запусків показали, що файл `data/raw/marketing_campaign.csv` не потрапляє в checkout, бо каталог `data/raw/` ігнорується Git.
3. **Ризики:** Головний практичний ризик self-hosted - не лише безпека, а й доступність. Якщо runner не запущений або неправильно налаштований, workflow не стартує взагалі. Також потрібно враховувати відмінності локального середовища (наприклад, `python3` замість `python` і обмеження Homebrew/PEP 668 для `pip`).

## Висновки
У ході лабораторної роботи було успішно побудовано повноцінний CI/CD конвеєр. Використання матричних стратегій дозволило значно скоротити час виконання за рахунок паралелізму, а фільтрація шляхів оптимізувала ресурси. Налаштування self-hosted runner показало переваги локального контролю над середовищем виконання, особливо для задач, що потребують доступу до великих локальних даних або специфічного апаратного забезпечення.
